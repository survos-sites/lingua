# lingua handoff — 2026-08-16

State at the end of the JSON-RPC session. Full reasoning lives in
[JSONRPC.md](JSONRPC.md); throughput measurements in
[BABEL-THROUGHPUT.md](BABEL-THROUGHPUT.md). This file is the short version and the
deploy checklist.

## What shipped

`POST /api/v1` (otezvikentiy/json-rpc-api 5.1) with two methods, both sharing their service
with the REST route they mirror, so the transports cannot drift:

| method | shares | replaces |
|---|---|---|
| `pullTranslations` | `TranslationPullService` | `POST /babel/pull` |
| `translateBatch` | `TranslationIntakeService` | `POST /batch-translate` |

**Both REST routes are unchanged and still work.** zm/bts/harvest parse them today, and tests
pin their existing response shapes.

Client side (`survos/lingua-bundle` ≥ 2.24.8): `LinguaClient` speaks either protocol,
selected by `LINGUA_PROTOCOL`, and reports every call through `$onCall` so `lingua:push` /
`lingua:pull` / `lingua:demo` narrate what is in flight instead of sitting silent.

Auth: one shared secret, `LINGUA_API_KEY`, checked by `LinguaApiKeyListener` over
`/api/v*`, `/batch-translate`, `/babel/pull`. **Inert while the var is empty** — which is
exactly today's behaviour, so it is safe to deploy before the key exists.

## Deploy checklist

Versions are already correct in `composer.json` / `composer.lock`
(`survos/lingua-bundle` and `survos/lingua-contracts` at **2.24.8**), and the app was
verified against those published packages, not against `mono/link` symlinks.

> **There is no `survos/lingua-bundle:2.24.9`.** mono is tagged 2.24.9, but split.yml only
> tags a package whose directory changed in that release range; 2.24.9 touched only
> elastic-bundle and search-bundle. The lingua packages went out in **2.24.8**. Requiring
> `^2.24.9` would fail to resolve. This is normal for this monorepo — check which tag
> actually carries a package before pinning it.

1. **Deploy lingua.** `/api/v1` appears; the key guard stays inert while `LINGUA_API_KEY`
   is empty; nothing else changes for existing callers.
2. **Set `LINGUA_API_KEY`** to the same value on lingua *and* on every caller
   (zm, bts, harvest), in the same window. Set it on lingua alone and callers get 401s.
   The key works over both transports, so this is independent of step 3.
3. **Set `LINGUA_PROTOCOL=rpc`** per calling app, once that app's lingua is known current.
   Default is `rest`, so doing nothing keeps today's behaviour. Not auto-detected on
   purpose: probing costs a round trip and a silent fallback would hide a misconfigured
   server.

Callers must also be on `survos/lingua-bundle` ≥ 2.24.8 before step 3 — an older client has
no RPC path at all.

## Verified

- 39 tests in lingua, 29 in lingua-bundle, all green against the **published** 2.24.8.
- Live against `lingua.wip`: `pullTranslations` with real hashes and `missing` isolating an
  unknown one; a two-element batch answered with per-element ids; `-32602` for bad params;
  `-32601` for an unknown method; REST byte-identical.
- Key guard, all six cases: unset → 200, missing → 401, wrong → 401, `X-Api-Key` → 200,
  `Bearer` → 200, `/health` untouched.
- zm and harvest lint clean (they symlink mono, so they took the client change immediately).

## Known and deliberate

- **`translations` still serialises as `[]` rather than `{}` when empty.** The bundle
  normalises every value to a PHP array before encoding, so this is unreachable without
  changing the response shape. `missing` is the fix that mattered.
- **`translateBatch` only queues.** Translation happens in the worker; poll
  `pullTranslations` for results. Making the write path synchronous is a separate question.
- **Three deprecations in the test output are upstream** — PHP 8.5 deprecated
  `SplObjectStorage::attach/detach/contains`, still used by the json-rpc bundle's
  `SerialisesPublicSurface`. Not filed yet; worth a small upstream issue.
